# Сохранения через ProfileStore

Используется предоставленный модуль MAD STUDIO из Workspace. Его исходник перенесён в `src/serverPackages/ProfileStore.luau`, а в Studio — в `ServerStorage.ServerPackages.ProfileStore`. Код библиотеки не изменён. ProfileStore и серверный сервис не находятся в Workspace, ReplicatedStorage или клиентских исходниках.

## Инварианты

- **SAVE-01** — Имена DataStore не меняются при обычном обновлении схемы: новое имя создаёт отдельную базу данных.
- **SAVE-02** — Оборудование хранится индексами позиций в GameConfig, виды — стабильными ключами `kind`. Перестановка каталога или смена ключа требует миграции.
- **SAVE-03** — В Profile.Data не попадают Model, Part, Vector3, CFrame, обработчики и анимации.
- **SAVE-04** — StudioMode=Mock включается только явно и только в Studio; при ошибке API сервис не подменяет хранилище памятью и не запускает игру с пустым профилем.
- **SAVE-05** — До успешной загрузки профиля (`PetDataReady`) и после потери сессии действия не меняют прогресс.

## Хранилища

Серверный конфиг: `src/server/data/Config.luau`.

| Запуск | DataStore | Ключ |
|---|---|---|
| Roblox Studio | PlayerProfiles_Studio_v1 | строковый UserId |
| Опубликованный сервер Roblox | PlayerProfiles_Live_v1 | строковый UserId |

Выбор определяется `RunService:IsStudio()`. Запуск опубликованного place внутри Studio всё равно использует тестовое хранилище. Данные игроков между этими двумя хранилищами не переносятся. Имена нельзя менять ради обычного обновления схемы: новое имя создаёт отдельную базу данных.

По умолчанию StudioMode=Persistent. Для сохранений между Play требуется Game Settings → Security → Enable Studio Access to API Services. В текущем Studio доступ проверен и работает. При недоступном API игрок получает понятное сообщение; сервис не подменяет постоянное хранилище временной памятью и не запускает игру с пустым профилем.

Для временных локальных экспериментов установить атрибут StudioMode="Mock" у ServerScriptService.PlayerData.Config в Edit до запуска Play и удалить после остановки. Этот режим действует только в Studio, не сохраняет данные между Play и никогда не включается автоматически. Без атрибута используется Persistent; в релизе атрибут игнорируется и всегда используется постоянное live-хранилище.

## Профиль

`Schema.luau` содержит шаблон, версию, проверку данных, расчёт офлайн-дохода и преобразование игрового состояния в сохраняемую таблицу. `Service.luau` управляет жизненным циклом профиля и предоставляет серверные Load, IsActive, GetData, SetSnapshot, Commit, RequestSave и Release.

Сохраняются деньги, скорость, Slow Mode, питомцы с ID, видом, весом и экипировкой, локальные позиции активных питомцев, яйца с видом, весом, позицией и временем вылупления, вместимость, коллекция, награды, настройки, офлайн-доход и все переносимые яйца в backpackEggs. Также сохраняются купленные и выбранные кирки/следы, уровни загона, дорожки и сумки, время игры. Номер базы не сохраняется: при входе выдаётся свободная база, относительные координаты применяются к ней. При отсутствии базы сессия профиля не начинается.

В профиль не записываются Model, Part, Vector3, CFrame, обработчики событий и анимации. Восстановленные записи копируются в игровое состояние; модели не добавляются в таблицы Profile.Data. Доход пересчитывается по активным питомцам, множитель — по выбранному следу. Полевую добычу нельзя сохранить до возвращения в Safe Zone. Старые записи TestChick остаются допустимыми и сохраняют прежний базовый доход.

## Жизненный цикл и защита

Load получает профиль через StartSessionAsync с отменой, если игрок ушёл или истёк лимит загрузки. Профиль связывается с UserId, дополняется через Reconcile и проходит проверку версии, типов, чисел, уникальности ID, вместимости и настроек. Ошибка подготовки, миграции или валидации восстанавливает исходные данные, завершает сессию и отклоняет вход; повреждённые поля не оставляют загрузку зависшей. До успешной загрузки действия UI и тренировки не изменяют прогресс.

После каждого игрового изменения данные обновляются в Profile.Data без запросов DataStore. ProfileStore сохраняет активную сессию автоматически раз в 60 секунд. Перед каждым сохранением OnSave снимает актуальное состояние. При выходе игрока вызывается EndSession. Rojo задаёт ProfileStore.Sandboxed=false: обработчики библиотеки могут вызвать BindableEvent SessionEnded сервиса и освободить игровое состояние. Финальное сохранение и ожидание запросов при закрытии сервера выполняет сама библиотека; отдельного конкурирующего цикла UpdateAsync больше нет. Получение офлайн-денег и награды коллекции дополнительно запрашивает сохранение с ограничением частоты.

Session locking предотвращает одновременную работу с одним профилем в разных серверах. При потере сессии игровые изменения прекращаются, база освобождается, игрок отключается с сообщением. Клиент не получает модуль, профиль или произвольный интерфейс записи DataStore; UI получает только необходимые игровые атрибуты. Старые прямые записи DataStore удалены из PetGameplay.

Автосохранение ограничивает потери при аварийном падении сервера, но не гарантирует сохранность изменений между последним успешным сохранением и аварией. Последнее подтверждённое сохранение отражается атрибутом LastDataSaveAt.

## Офлайн и перенос старого формата

В схеме версии 1 есть массив backpackEggs: переносимые яйца с id, kind и weight, без таймера роста. Reconcile добавляет пустой массив существующим профилям. Неразмещённые питомцы по-прежнему хранятся в pets с equipped=false. Tool создаются из записей при входе и респавне; Instance не сохраняются. Старые carriedKind/carriedPet однократно преобразуются в backpackEggs либо запись pets, без дублирования существующего ID; после преобразования старые поля очищаются. Имена DataStore и версия схемы не меняются. Проверка ID охватывает pets, eggs и backpackEggs; общий лимит учитывает все три массива.

При входе начисляется незабранный доход только за первые 24 часа отсутствия; последующее время доход не добавляет. Яйца, вылупившиеся во время отсутствия, занимают свободные активные слоты по времени готовности, при равенстве — по ID, и учитываются в доходе с момента вылупления. Такой же порядок используется онлайн и в Grow All. Незабранная офлайн-награда и Cash ограничены числовым пределом 1e18, поэтому начисление и Claim не создают недопустимый профиль. Claim переносит сумму в баланс в пределах этого ограничения и обнуляет офлайн-награду; флаг награды коллекции также сохраняется.

Если старый одиночный предмет не представлен существующим ID, а все 200 мест заняты, миграция сохраняет carriedKind/carriedPet до освобождения места. Вход разрешён; предмет не удаляется и не увеличивает три массива сверх лимита. После освобождения места сервер переносит его в обычный инвентарь и создаёт Tool. Размещение других предметов, респавн и повторный вход не очищают ожидающий предмет.

Старая конечная офлайн-сумма выше 1e18 приводится к этому пределу перед проверкой профиля. NaN, Infinity и неверные типы по-прежнему отклоняются.

Для live-профиля предусмотрен однократный перенос прежнего формата из PetBases_v1, только если новый профиль ещё не инициализирован. Старое хранилище только читается, не удаляется и не перезаписывается. Studio никогда не обращается к нему. Ошибка чтения или проверки старых данных останавливает загрузку; пустое состояние не подменяет сохранённый прогресс. Управление — MigrateLegacyLive в серверном конфиге.

## Проверки

Статус — в [verification.md](verification.md). Ранее в настоящем Studio DataStore подтверждены запись и повторная загрузка после Stop/Play: деньги, ID питомца, слоты, скорость, Slow Mode, настройки, переносимое яйцо и размещённое яйцо. Яйцо вылупилось за время отсутствия; начисление офлайн-дохода и защита от повторного Claim проверены. Повторное получение коллекционной награды отклонено. Клиентская проверка подтвердила отсутствие ServerPackages, PlayerData и ProfileStore в доступном дереве.

`tools/verify-profiles.luau` использует отдельный ProfileStore.Mock: проверяет разные пространства имён, шаблон, недопустимые числа и ID, будущую версию схемы, офлайн-доход и лимит, запрет второй активной сессии, освобождение/повторную загрузку, Reconcile и JSON-сериализацию. Игровые ключи и live-хранилище тест не меняет.

Сборка Rojo и синтаксис изменённых серверных исходников проверены. Опубликованный live-сервер, передача сессии между двумя реальными серверами и миграция существующего live-ключа пока не тестировались.

API и жизненный цикл сверены с [официальной документацией ProfileStore](https://madstudioroblox.github.io/ProfileStore/api/).
